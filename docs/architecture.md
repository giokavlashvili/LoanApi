# Project architecture guide

Deep reference for this Clean Architecture / CQRS boilerplate. Agents should prefer `.cursor/rules/` and `.cursor/skills/` for day-to-day work; read this file when you need full detail.

## What this repository is

A **Clean Architecture / CQRS boilerplate** for ASP.NET Core (net10.0) Web APIs. It is copied as the starting point for new projects, so the loan domain (`LoanApplication`, `LoanType`, `Currency`, `LoanStatus`) is **sample content demonstrating the patterns**, not the point of the repo. Expect it to be renamed and its domain replaced.

The project name is not baked into the code: assemblies/namespaces are the generic `Domain`, `Application`, `Infrastructure`, `WebApi`, and the string "LoanApi" appears only in the solution *filename* and repo folder name. When repurposing:

- Rename `LoanApi.sln` and the repo folder (solution *contents* need no edits).
- `WebApi/appsettings.json`: `ConnectionStrings:DefaultConnection` (`Database=LoanDB`) and `JWT:Secret`.
- Replace the sample vertical slices: `Domain/Entities`, `Domain/Events`, `Domain/Enums`, `Domain/Repositories`, `Application/LoanApplications`, `Application/Currencies`, `Application/LoanTypes`, `Infrastructure/Persistence/{Configurations,Repositories}`, `WebApi/Controllers/{LoanApplication,Currency,LoanType}Controller.cs`, the seed data in `ApplicationDbContextInitialiser.TrySeedAsync`, `WebApi/Resources/localization.json`, and the existing `Infrastructure/Migrations` (delete and re-create an Initial migration for a new domain).
- Keep: `Domain/Common`, `Application/Common`, `Application/Authenticate`, `Infrastructure/Identity`, `WebApi/{Filters,Middlwares,Extensions,Localization,Services}` -- that is the reusable skeleton.

## Commands

```bash
dotnet build LoanApi.sln -p:SkipNSwag=True
```

```bash
dotnet test LoanApi.sln -p:SkipNSwag=True
```

Run a single test / fixture (NUnit + `dotnet test` filter):

```bash
dotnet test Domain.UnitTests/Domain.UnitTests.csproj --filter "FullyQualifiedName~LoanApplicationTests.UpdateLoanApplicationStatus_WhenCalled_ChangeStatus"
```

Run the API (Swagger UI at `/swagger`; http profile = 5041, https = 7233):

```bash
dotnet run --project WebApi/WebApi.csproj --launch-profile https
```

EF Core migrations -- `Infrastructure` holds the migrations, `WebApi` is the startup project:

```bash
SkipNSwag=True dotnet ef migrations add <Name> --project Infrastructure --startup-project WebApi
```

```bash
dotnet ef database update --project Infrastructure --startup-project WebApi
```

`SkipNSwag` has to be an **environment variable** here, not `-p:SkipNSwag=True`: `dotnet ef` forwards everything after `--` to the *application*, not to MSBuild, so the flag never reaches the build and NSwag runs anyway. PowerShell equivalent: `$env:SkipNSwag = "True"; dotnet ef migrations add ...`. Without it the scaffold build fails wherever the NSwag tool isn't restorable.

Two expected-and-harmless noises from `dotnet ef`: a tools/runtime version warning (the installed `dotnet-ef` is 9.0.7 against EF Core 10.0.10 -- it works, it just nags), and a `HostAbortedException` stack trace, which is how the EF tooling stops the host after building the service provider.

Notes on the build:

- A **Debug build of `WebApi` runs NSwag as a post-build step** (`NSwag` target in `WebApi/WebApi.csproj`): it generates `WebApi/wwwroot/api/specification.json` and the Angular client `WebApi/ApiClient/web-api-client.ts`. It boots the app's OpenAPI document provider, so a DI/startup regression fails the *build*, not just runtime. It does not need a database. Pass `-p:SkipNSwag=True` to skip it (faster, and required if the NSwag tool isn't restorable).
- In Development, startup applies migrations and seeds (`Program.cs`), so `dotnet run` needs SQL Server at `localhost\SQLEXPRESS`. To run without one, set `"UseInMemoryDatabase": true` in `WebApi/appsettings.json` (switch honored in `Infrastructure/Common/Extensions/ConfigureServices.cs`).
- Seeded dev credentials: `administrator@localhost` / `Administrator1!` (role `Administrator`).

### Secrets

`WebApi/appsettings.json` ships `JWT:Secret` and `Otp:Secret` as **empty strings** -- both are
validated with `ValidateOnStart()` (see `JwtOptions`, `OtpOptions`), so a real deployment that
does not supply them fails loudly at boot naming the missing setting, rather than throwing on the
first login or the first issued code. `WebApi/appsettings.Development.json` carries placeholder
values for both (beside the `Otp:StaticCode` escape hatch), so clone-and-run still works without
any extra setup.

To run against your own values instead of the committed placeholders, use user secrets (the
project already has a `UserSecretsId` in `WebApi/WebApi.csproj`):

```bash
dotnet user-secrets set "JWT:Secret" "<a real secret, at least 32 characters>" --project WebApi
dotnet user-secrets set "Otp:Secret" "<a real secret>" --project WebApi
```

Production should source both from a real secret store rather than configuration files or user
secrets. `Infrastructure` already references `Azure.Identity` (currently unused elsewhere) if Key
Vault is the destination.

## Architecture

Project references flow inward: `WebApi -> Infrastructure -> Application -> Domain`. Note `Infrastructure` references `Application` (not the reverse) -- abstractions such as `IApplicationDbContext`, `ICurrentUserService`, `IDateTime`, `IUserService`/`IIdentityService`, `IJwtTokenGenerator`, `IOtpService`, `IOtpCodeHasher` and `ISmsSender` live in `Application/Common/Interfaces`, while repository/unit-of-work abstractions live in `Domain/Repositories`. `Domain` declares no outbound service contracts at all: `IUserService` and its `User` projection used to sit in `Domain/Common`, which had the innermost layer describing a dependency it never called. Each layer exposes one `ConfigureServices` extension (`AddApplicationServices`, `AddInfrastructureServices`, `AddWebUIServices`) composed in `WebApi/Program.cs`.

### Where a service lives

**Dependency direction decides, not subject matter: policy in `Application`, mechanism in `Infrastructure`.** A class that only orchestrates abstractions belongs in `Application` no matter how technical its topic sounds; a class that *is* the technical detail belongs in `Infrastructure`.

The OTP feature is the worked example of the split. `OtpService` lives in `Application/Otp/Services` and is registered in `AddApplicationServices`: it contains no infrastructure, only a sequence of decisions over `IOtpVerificationRepository`, `IOptionsMonitor<OtpOptions>`, `IOtpCodeHasher`, `ISmsSender`, `IDateTime` and `IUnitOfWork`. The mechanisms it depends on stay behind in `Infrastructure` — `HmacOtpCodeHasher` (crypto) and `LoggingSmsSender` (a vendor adapter) — and are registered in `AddInfrastructureServices`. It sat in `Infrastructure` purely by habit, and the giveaway was that its test already lived in `Application.UnitTests`.

Two things this criterion is *not*:

- **It is not "does it touch EF".** `Application` references `Microsoft.EntityFrameworkCore` by design, because `IApplicationDbContext` exposes `DbSet<T>`; `OtpService.IssueAsync` catches `DbUpdateException` there and that is fine. Hiding one exception type behind a new `IUnitOfWork` member would buy nothing. (Making `Application` genuinely EF-free is a real but much larger question about `IApplicationDbContext`'s surface, and is not on the table.)
- **It is not a reason to move `IdentityService` or the repositories.** Those wrap ASP.NET Identity and EF respectively — they are mechanism, and they stay.

Because `OtpService` is neither a handler, a validator, a mapping profile nor an EF configuration, it is one of the few things needing an explicit DI line rather than being assembly-scanned.

### Time

`IDateTime` exposes a single member, `UtcNow`, and `DateTimeService` (registered as a singleton) is the only place in the solution permitted to read the system clock -- every persisted timestamp (`LoanApplications`, `OtpVerifications`, `Logs`, JWT expiry) is on the same UTC clock. A `Directory.Build.props` at the repository root adds `Microsoft.CodeAnalysis.BannedApiAnalyzers` with `BannedSymbols.txt` banning `DateTime.Now`/`UtcNow`/`Today` and `DateTimeOffset.Now`/`UtcNow` (rule `RS0030`, `WarningsAsErrors`), so a raw clock read anywhere else is a build error, not a review comment. Test projects (`Domain.UnitTests`, `Application.UnitTests`) opt out via `NoWarn` because they legitimately construct fixed instants. Before this, `DateTimeService` returned *local* time while the Serilog sink and the log retention purge (`LogRetentionService`) read `DateTime.UtcNow` directly -- two tables in one database were timestamped on clocks that differed by the UTC offset, and local time is not monotonic across a DST fall-back.

### Request flow

Controller (thin, `ApiControllerBase.Mediator.Send`) -> `ValidationBehavior` -> `PerformanceBehavior` -> `OtpVerificationBehavior` (when command implements `IRequireOtpVerification`) -> `OperationConfirmationBehavior` (when it implements `IRequireOperationConfirmation`) -> handler -> aggregate repository -> `IUnitOfWork.SaveChangesAsync` -> `ApplicationDbContext.SaveChangesAsync` -> domain events dispatched -> response; exceptions shaped by `ApiExceptionFilterAttribute`.

**Queries do not take that path.** A query handler injects `IApplicationDbContext` and projects with `ProjectTo` straight to its DTO: no repository, no change tracker, no entity materialised only to be mapped and discarded. The read side has no invariants to protect, so it does not go through the write model.

### Conventions that matter when adding code

- **Vertical slices in `Application`**: `Application/<Feature>/{Commands,Queries,Dtos,Validators,EventHandlers}`. The MediatR request *and* its handler live in the same file (e.g. `CreateApplicationCommand.cs` holds `CreateApplicationCommand` + `CreateApplicationCommandHandler`). Commands/queries are `record`s implementing `IRequest`/`IRequest<T>`.
- **Registration is assembly-scan based** -- validators, MediatR handlers, AutoMapper profiles, and EF `IEntityTypeConfiguration`s are all discovered automatically. New files in the right place need no DI wiring.
- **DTOs map via `IMapFrom<T>`** (`Application/Common/Mappings`): implement the interface for the default map, or override `Mapping(Profile)` for custom members. `MappingProfile` reflects over the Application assembly.
- **Business rules live in the domain entity**, not the handler. Entities have `private set` properties, a `static Create(...)` factory and mutator methods that throw `DomainValidationException` and call `AddDomainEvent(...)` (see `Domain/Entities/LoanApplication.cs`). Handlers only orchestrate: call the entity, save.
- **Audit fields are stamped at the save boundary, not passed in.** `AuditableEntityInterceptor` (`Infrastructure/Persistence/Interceptors/`) is a `SaveChangesInterceptor` that fills `Created`/`CreatedBy` on `Added` entries and `LastModified`/`LastModifiedBy` on `Modified` ones, reading `ICurrentUserService` and `IDateTime`. So `LoanApplication.Create` takes four business arguments and no audit ones, and `#pragma warning disable CS8604` is gone from the handlers that used to paper over the nullable `UserId`. Details worth knowing:
  - It is resolved **from the container**, which is why both branches of `AddInfrastructureServices` use the two-argument `AddDbContext((provider, options) => …)` overload — the single-argument one cannot reach it. It is registered on the **in-memory branch too**; attached only to SQL Server, auditing would stop working wherever `UseInMemoryDatabase` is true, which includes the tests.
  - It is registered **scoped as a deliberate floor, not because it has to be**. Both of its dependencies are singletons today (`ICurrentUserService` in `AddWebUIServices`, `IDateTime` in `AddInfrastructureServices`), so a singleton would work equally well. Scoped keeps it correct if `ICurrentUserService` ever becomes per-request — the direction that type is likeliest to move — where a singleton interceptor holding it would be a captive dependency.
  - It fills `Created`/`CreatedBy` only where the entity left them unset. `OtpVerification.Create` takes its own `created` and derives `CreatedBy` from the challenge's user, and the resend cooldown reads those values back — overwriting them would break it.
  - `Modified` also covers an entry whose owned entities changed, since EF reports the parent as `Unchanged` in that case. Nothing in this model is owned yet; the check is there so adding one does not silently create a gap.
  - **The entity can no longer enforce `InvalidUser`**, because it never sees a user id. That invariant moved to the handlers as `ICurrentUserService.RequireUserId()` (`Application/Common/Extensions/CurrentUserServiceExtensions.cs`), which throws the same `DomainValidationException("InvalidUser")`; without it a request with no authenticated caller would persist a row with a null `CreatedBy` and no complaint. It was moved, not dropped, and the `Domain.UnitTests` cases were replaced by equivalents in `Application.UnitTests`.
    - That guard is **expected never to throw in production, and is not dead code**. Every command calling it sits behind an `[Authorize]` controller and `JwtTokenGenerator` always emits `ClaimTypes.NameIdentifier`, so an authenticated request always carries an id. It is the last guard on a real constraint — `LoanApplicationConfiguration` marks `CreatedBy` `IsRequired()` — turning what would otherwise be a `NOT NULL` violation deep in `SaveChanges` (a 500) into a localized 400 at the top of the handler. Removing `[Authorize]`, or issuing a token without that claim, makes it live.
  - Ordering against domain events: `SaveChangesAsync` dispatches events *before* the interceptor runs, so an event handler sees unstamped audit fields. No handler reads them today; one that needs `Created` or `LastModifiedBy` should take it from the command.
  - **A no-op update no longer bumps `LastModified`** — a deliberate behaviour change, and invisible at the call site. `LoanApplication.Update` used to assign `LastModified`/`LastModifiedBy` itself, so EF always saw a modified property and always wrote the row. A command carrying values identical to the stored ones now changes nothing, the entry stays `Unchanged`, and the interceptor's `Modified` branch never runs: no write, no `RowVersion` churn. Note the asymmetry it leaves — the aggregate still raises `ApplicationUpdatedEvent` unconditionally, so such a request publishes an event with no matching audit bump. Make the event conditional on an actual change if that ever matters.
- **EF mapping is Fluent API only; `Domain/Entities` carries no annotations.** `LoanApplication` used to declare `[ForeignKey]` on its `LoanType`/`Currency` navigations while every other entity was configured in `Infrastructure/Persistence/Configurations`. Both relationships are now `HasOne(...).WithMany().HasForeignKey(...)` in `LoanApplicationConfiguration`, which produces an identical model — the confirming migration scaffolded after the change was empty. The one surviving annotation is `[NotMapped]` on `BaseEntity.DomainEvents`: it is on the base type, and restating it in every entity's configuration would be worse than one attribute. The `[NotMapped] public User? CreatedByUser` property went away entirely — nothing ever populated it, and it was the only public settable property on an otherwise encapsulated aggregate. Removing it is also what freed `User` to move out of `Domain`.
- **FluentValidation validators handle input/lookup validation** (e.g. "does this CurrencyId exist"); they are injected with `IApplicationDbContext` and `IStringLocalizer`. An existence check is a read, so it queries the context rather than going through a repository.
- **Lookup rules are async.** `ValidationBehavior` is the only FluentValidation entry point (`ValidateAsync`); there is no MVC auto-validation. Existence/I/O checks use `MustAsync`/`CustomAsync` with `AnyAsync`/`FirstOrDefaultAsync` (and Identity's async APIs) so they can honour `CancellationToken` without blocking. Pure format/range rules may stay synchronous (`Must`/`NotEmpty`/…). Smoke coverage: `Infrastructure.UnitTests/Validators/ValidatorLookupAsyncTests.cs`.
- **Domain events**: entities queue events; `ApplicationDbContext.SaveChangesAsync` calls `MediatorExtensions.DispatchDomainEvents` *before* persisting, publishing them to `INotificationHandler`s in `Application/<Feature>/EventHandlers`. **The aggregate raises all of its own events, deletion included** — `LoanApplication.Delete()` raises `ApplicationDeletedEvent` and the handler calls `entity.Delete()` before `repository.Remove(entity)`. The handler used to construct that event itself, which worked only because dispatch precedes `SaveChanges` and the entity is still tracked in the `Deleted` state: a detail no handler should have to know, and the one event in the aggregate not raised by the aggregate. See also the ordering caveat under *Known state / gotchas*.
- **`IRepository<TEntity> where TEntity : BaseEntity`** is a deliberately **general-purpose** surface, so an unforeseen feature does not have to widen it. The constraint is `BaseEntity` rather than `IAggregateRoot` because this is reusable boilerplate: an entity that is not an aggregate root still needs somewhere to live. `IAggregateRoot` survives as documentation of which entities own a consistency boundary (`LoanApplication`, `OtpVerification`), not as a compile-time gate.
  - *Composable*: `Query()` / `QueryAsNoTracking()` return `IQueryable<TAggregate>` for anything the named members do not cover (grouping, joins, a projection).
  - *Reads*: `GetByIdAsync`, `FirstOrDefaultAsync`, `SingleOrDefaultAsync`, `ListAsync`, `PageAsync`, `AnyAsync`, `CountAsync` — each taking an optional filter, ordering and include shaper.
  - *Writes*: `AddAsync`, `AddRangeAsync`, `Update`, `UpdateRange`, `Remove`, `RemoveRange`.

  Three properties of that surface are load-bearing, and each replaces something that used to be a bug:
  - **Includes are a typed shaper, not a string.** `include: q => q.Include(a => a.Currency).ThenInclude(…)` instead of `includeProperties: "Currency,LoanType"`. A typo in the old string returned a row with an unloaded navigation — no exception, just an empty name in the DTO — and no rename or find-usages ever followed it. The delegate is compiler-checked and supports chains.
  - **`Update` is a no-op for a tracked aggregate**, by design. `DbSet.Update` marks every property modified, rewriting columns that never changed and churning the `RowVersion` concurrency token; the change tracker already holds the delta. `Repository.Update` therefore calls it only when the entry is `Detached` — the disconnected case where there genuinely is no tracked original. So `entity.Mutate(); await uow.SaveChangesAsync();` is the normal write path and needs no `Update`, while a `QueryAsNoTracking()` result does.
  - **Reads default to tracked** (`asNoTracking: false`). A silently-dropped mutation is a bug; a redundant tracking entry is a perf nit. Read-only paths opt in with `asNoTracking: true`.

  `IRepository` names only BCL types (`IQueryable`, `Expression`, `Task`) — EF appears solely in the Infrastructure implementation, so `Domain` keeps no persistence dependency. `PageAsync` returns `(Items, TotalCount)` off one composed query so the two cannot disagree, and rejects a non-positive page with `DomainValidationException("InvalidPageNumber"/"InvalidPageSize")` — the same keys `GetApplicationsQueryValidator` uses, so the message is identical whether the edge or the repository caught it.
- **`IAggregateRoot`** (`Domain/Common/`) marks the entry point to an aggregate. Roots: `LoanApplication`, `OtpVerification`. Not roots: `Currency` and `LoanType`, which are reference data with no behaviour and no invariants and therefore **have no repository at all**; and `Log`, which is not a domain concept (the Serilog sink writes it, EF owns only the schema).
- **`IUnitOfWork` is `SaveChangesAsync` and nothing else** — the transactional boundary. It used to carry a property per repository, which made it a service-locator: a handler injected the registry and reached through it, so its real dependencies were invisible from its constructor and every test had to stub repositories the handler never touched. Handlers now inject the repositories they use. It is also not `IDisposable` — the `DbContext` is container-owned.
- **Adding an aggregate**: mark the root `IAggregateRoot`, interface in `Domain/Repositories`, implementation in `Infrastructure/Persistence/Repositories`, an `AddScoped` line in `AddInfrastructureServices`, and inject it into the handler. Nothing to add to `IUnitOfWork`. Repositories are the one thing that is *not* assembly-scanned, so a missing registration fails to resolve at startup.
- **Read-side projection**: query handlers use `.AsNoTracking().ProjectTo<TDto>(_mapper.ConfigurationProvider)`. `ProjectTo` builds a member-init expression tree, so **projected DTOs need public setters** — `IMapper.Map` tolerated `private set` only because it assigns by reflection. A `MapFrom` containing a method call will not translate; map it explicitly rather than letting it fall back to materialising entities. `GetApplicationsQuery` derives its count and its page from one `IQueryable`, so the two cannot drift apart the way two repository methods could.
- **Controllers**: inherit `ApiControllerBase`, route `api/v1/[controller]` with `[Route(nameof(Action))]` per action, `[Authorize]` at class level for protected controllers. One line per action delegating to `Mediator`.

### Cross-cutting behavior

- **Errors -> HTTP**: `WebApi/Filters/ApiExceptionFilterAttribute.cs` maps `ValidationException` (400 + `ValidationProblemDetails`), `NotFoundException` (404), `Unauthorized`/`ForbiddenAccessException`, and `DomainValidationExceptionWrapper` (400, message localized). `ValidationBehavior` is what wraps a raw `DomainValidationException` into `DomainValidationExceptionWrapper`. Anything unmapped is caught by `UnhandledExceptionHandlerMiddlware` and returned as a generic 500. **Domain exception messages are localization keys, not user text** -- add the key to `WebApi/Resources/localization.json` (`ka-GE` / `en-US`).
- **Localization**: the `x-sys-language` request header sets the culture (`SysLanguageMiddleware`); `JsonStringLocalizer` (registered as a singleton `IStringLocalizer`) reads `Resources/localization.json` from disk at construction. The header is stripped from the generated TS client via `excludedParameterNames` in `nswag.json`.
- **Auth**: ASP.NET Identity (`ApplicationUser : IdentityUser` with FirstName/LastName/PersonalNumber/BirthDate) + JWT bearer. Issuer/audience validation is disabled by design in the template.
  - **Token minting is a separate service.** `IdentityService` was doing four jobs at once — user lifecycle, authorization, JWT construction and event publishing. The `JwtSecurityToken`, the `SymmetricSecurityKey`, the claims and `JwtOptions` (`Secret`, `ExpireMinutes`) now live in `JwtTokenGenerator` behind `IJwtTokenGenerator`, and `AuthenticateAsync` reduces to: find user → check password → get roles → delegate. It is registered as a **singleton** — both dependencies are singletons and it reads `IOptionsMonitor.CurrentValue` per call, so a rotated secret still takes effect.
  - **Bad credentials are 401, not 404.** `AuthenticateAsync` used to throw `NotFoundException("User not found")` for a wrong password, which the exception filter mapped to `404`. It now throws `InvalidCredentialsException` (`Application/Common/Exceptions/`), mapped to `401` in `ApiExceptionFilterAttribute` with the `InvalidCredentials` key. One exception covers both an unknown user and a wrong password, and neither branch is logged: distinguishing them would turn the endpoint into a user name oracle.
  - **`UserRegisteredNotification` is not a domain event, and cannot be one.** A successful `CreateUserAsync` publishes it straight through `IMediator`, which is a second event path alongside `BaseEntity.DomainEvents` — so here is the reasoning, because an unexplained second path is what makes a reader distrust both. `MediatorExtensions.DispatchDomainEvents` scans `ChangeTracker.Entries<BaseEntity>()`, and `ApplicationUser : IdentityUser` can never be a `BaseEntity`: Identity's `UserStore`/`UserManager`/`IdentityDbContext<TUser>` all require that base, C# allows only one, and the two disagree about identity anyway — `BaseEntity.Id` is an `int` with a private setter, `IdentityUser.Id` a `string` GUID that Identity generates. The **save path is not the obstacle**, which is worth knowing before anyone tries to fix the wrong end: `AddEntityFrameworkStores<ApplicationDbContext>` means Identity persists through the same context, so the `SaveChangesAsync` override does run and dispatch does happen during registration — it just finds nothing, because the user is not a `BaseEntity`. (`ApplicationUser` used to carry a hand-rolled `DomainEvents` list and `AddDomainEvent` for exactly this reason-shaped hole; they were unreachable by the dispatcher and nothing ever called them, so they are gone. They were a trap: they looked like a working extension point and would have swallowed any event queued on them.) Its predecessor was named `UserCreatedEvent` and derived from `BaseEvent`, which *implied* it travelled the aggregate path when nothing ever attached it to an entity. Renaming it to a notification (in `Application/Authenticate/Notifications`, handled from `NotificationHandlers`) makes the difference visible at the call site instead of leaving it to be discovered. The alternative — a domain `User` aggregate mirroring the Identity user — was rejected as substantially more moving parts for a product that does not otherwise need one; if that changes, this notification is what should move onto it. The publish also sits **inside** the success branch: unconditional, it announced users that `CreateAsync` had just refused to create.
- **MediatR behaviors are constrained `where TRequest : notnull`, not `where TRequest : IRequest<TResponse>`.** This is load-bearing. MediatR.Contracts 2.x made `IRequest` and `IRequest<T>` *unrelated* interfaces, so a void command (`: IRequest`) is not an `IRequest<Unit>`. MediatR still resolves `IPipelineBehavior<TCommand, Unit>` for it, the tighter constraint cannot be satisfied, and **the DI container silently skips the registration instead of failing** -- which left every void command (`UpdateApplicationCommand`, `UpdateApplicationStatusCommand`, `DeleteApplicationCommand`) with no validation, no performance logging and no OTP gate, surfacing domain exceptions as raw 500s. `OtpVerificationBehaviorTests.Handle_ForAVoidCommand_StillGate` fails to compile if the constraint is ever tightened back.
- **Two step verification (OTP)**: a command opts in by implementing `IRequireOtpVerification` (`Application/Common/Otp/`) and declaring `ChallengeId` + `[SensitiveData] OtpCode`. `OtpVerificationBehavior` does the rest: a request without a code gets a challenge issued and texted, then a **428 Precondition Required** carrying `challengeId`/`expiresAt`; the caller re-sends the same payload with the code. **Adding OTP to a new operation is implementing one interface -- there is no per-feature plumbing.** Sample: `RegisterUserCommand` (no user exists yet, so it overrides `OtpRecipient => PhoneNumber`; everywhere else leaving it null reads the number off the authenticated account, which is what stops a caller redirecting their own code to a phone they control).
  - `OtpPurpose` defaults to the command type name, so a code issued for one operation cannot be spent on another, and no registry needs maintaining.
  - **`OtpService.VerifyAsync` saves in a `finally`.** `OtpVerification.Verify` increments `AttemptCount` and *then* throws on a wrong code; saving only on the happy path would roll that increment back every time, `MaxAttempts` would never be reached, and six digits would be brute-forceable at leisure. The challenge is loaded tracked, so the increment reaches the database without any `Update` call.
  - `OtpService` injects `IOtpVerificationRepository` and `IUnitOfWork` directly. Its three lookups (`GetByChallengeIdAsync`, `CountRecentAsync`, `GetLatestAsync`) stay on the repository rather than moving to a query handler because each one feeds a decision that mutates the aggregate — they are write-side reads.
  - `OtpService` lives in **`Application/Otp/Services`**, not `Infrastructure` — see *Where a service lives* above.
  - The challenge stores a `RequestHash` -- the payload with `ChallengeId`/`OtpCode` removed. Without it a caller could confirm a harmless request and then re-send a different one with the same code.
  - Codes are stored as a **keyed** HMAC (`Otp:Secret`), never plaintext: an unkeyed digest of six digits is a million candidates and reverses instantly from a leaked table.
  - `ISmsSender` has one implementation, `LoggingSmsSender`, which **logs the code instead of sending it** so the flow is runnable with no vendor account. It warns on every send. Replace it with a real provider (one class, one line in `AddInfrastructureServices`) before production.
  - OTP-carrying property names are in `RequestLogging:SensitiveProperties` **and** `LogRedactor.DefaultSensitiveProperties`. Both are needed: `BuildKeySet` uses the configured list *instead of* the defaults when config supplies one, so adding to only one leaves live codes in the `Logs` table.
- **Two step verification has two topologies, and the choice is not about how sensitive the operation feels.** They share the whole OTP core and differ in **who holds the payload between the two calls**. The inline gate above keeps it on the client, which is cheap and stateless but means only whoever composed the request can ever complete it. `IRequireOperationConfirmation` (`Application/Common/Confirmation/`) captures the serialized command into a `PendingOperation` aggregate instead, which is what makes an approval by a *different* user, on a different device, or hours later expressible at all. `UpdateApplicationStatusCommand` moved onto it with `ConfirmationPolicy.DifferentUser`; `RegisterUserCommand` deliberately did not, because its payload carries a password and a parked operation persists what it captures. **That is the criterion: what is in the payload, and who has to confirm it.**
  - **The marker interface is empty, and must stay empty.** The obvious design puts `Guid? OperationId` on it and has the behaviour read "null means initiate, set means already confirmed". Commands are model bound straight from the request body, so that property is caller controlled: anyone could post the ordinary endpoint with an arbitrary operation id and the behaviour would wave the command through with **no pending operation, no code, and no confirmation of any kind** — on `LoanApplicationController`, whose `[Authorize]` is bare, that is the entire user base. `[JsonIgnore]` would close it, but it is a per-command opt-in whose failure mode is silent total bypass, on boilerplate meant to be copied. The confirmed-execution signal therefore travels out of band in the scoped `IOperationExecutionContext`, set only by `ConfirmOperationCommandHandler` around its re-dispatch.
  - **A code is issued at initiate only under `SameUser`.** That is the one policy where the confirmer's phone number is knowable at that point; under four eyes the approver is somebody the server has not met, and texting the initiator would send the code to the one person who must not be able to complete the operation alone. The approver asks for their own through `POST api/v1/Operations/{id}/challenge`, which runs the same policy check before it texts anything.
  - **`ChallengeId` is carried by the caller, not stored on the operation.** `OtpService.ResendAsync` mints a **new** challenge id and retires the old, so a stored one would be stale the moment anyone asked for a fresh message, and keeping it current would mean teaching the OTP layer about pending operations. It costs nothing: the binding is the request hash — `Hash(operationId, discriminator)` — so a challenge issued for another operation is refused with `OtpRequestMismatch`. The same reasoning is why the anonymous `ResendOtp` endpoint is safe.
  - **`purpose` is the discriminator alone, and that is a deliberate trade.** `OtpService` uses `Purpose` as both the replay scope *and* the throttle key for `MaxPerRecipientPerHour`/`ResendCooldown`; folding the operation id in would scope challenges perfectly per operation and **silently disable the SMS rate limit**, since every operation would get a fresh bucket. The cost is that only one live code per operation type exists at a time — initiating a second approval retires the first one's code, and each is individually recoverable through resend but only one at a time. Note also that `MaxPerRecipientPerHour` defaults to 5, which is tuned for registration: an approver doing six approvals in an hour is throttled, and the value cannot be raised for approvals without also raising it for registration.
  - **Discriminators are stable and versioned** (`loan.status.update.v1`), never CLR type names — they are persisted on every parked row and must survive the namespace renames a forked boilerplate gets. `OperationTypeRegistry` is the only way a stored discriminator is resolved; a payload parked under one that no longer exists fails closed rather than deserializing into whatever the type looks like now.
  - **The registry throws at startup** for a duplicate discriminator, either declaration half missing, a type opting into both topologies, or any property that is `[SensitiveData]` or *named* like one in `LogRedactor.DefaultSensitiveProperties` — recursing into nested types and collection elements. The name check is the one that matters: `RegisterUserCommand.Password` carries no attribute, so an attribute-only scan would wave through the single command the guard most needs to stop. It is registered as a constructed instance rather than behind a factory lambda, because a factory resolves lazily and "fails at boot" has to mean while the container is still being composed.
  - **Re-validation is the safety net for deferred execution.** The captured command goes back through the whole pipeline, so `ValidationBehavior` and the domain invariants run again against state that moved while it was parked — `LoanApplication.UpdateStatus` throwing `ApplicationAlreadyProcessed` is what stops a stale approval overwriting a loan somebody else already actioned.
- **Logging**: Serilog, composed in code by `AddApplicationLogging` (`WebApi/Extensions/LoggingConfiguration.cs`). Only *levels* live in config (the `Serilog` section of `appsettings.json`); sinks and the column mapping are C#, so a typo is a compile error rather than a silently dead column. `Program.cs` creates a `CreateBootstrapLogger()` before the container exists and ends with `Log.CloseAndFlush()` in a `finally` -- the database sink batches, so skipping the flush loses the tail.
  - **There is no `Logging` section in `appsettings.json`, deliberately.** `Microsoft.Extensions.Logging` filters run *before* Serilog sees an event, so keeping one would silently pre-filter events that `Serilog:MinimumLevel:Override` was going to allow. Level config has exactly one home.
  - **`LoggingMiddleware` writes one structured row per request** -- correlation id, method, url, status, duration, user, client ip, and the redacted request/response bodies. It is registered **outermost** (before `UseApplicationExceptionHandler`) so it observes the final status code and body of everything below it, including 500s. Its `try/finally` guarantees a row even when the request throws.
  - **Log columns come from two sources.** Message-template holes and `ILogger.BeginScope` values are both just structured properties to Serilog; `BuildColumnOptions` binds them to columns **by matching name**, so adding a property named like a column is all it takes. Request context that no single call site knows (correlation id, url, method, ip, username) is attached by `HttpContextEnricher` -- the replacement for NLog's ambient `${aspnet-*}` renderers, and the reason a warning raised deep in a handler still carries its request. `DefaultChannelEnricher` supplies `Channel=Api` via `AddPropertyIfAbsent`, which is why the middleware's explicit `Request` value wins. Property names are declared in `Application/Common/Logging/LogProperties.cs` and must stay in sync with `Domain/Entities/Log.cs` and `BuildColumnOptions`.
  - **`AutoCreateSqlTable` is off** -- EF owns the `Logs` schema. The consequence: the column set in `BuildColumnOptions` must match the table *exactly*, standard columns the table lacks (`Properties`, `MessageTemplate`, `LogEvent`, `TraceId`, `SpanId`, and the IDENTITY `Id`) are removed from `Store`, and a mismatch fails the whole batch reporting only to `Serilog.Debugging.SelfLog`. This is the one place where a mistake is silent, which is why `EnableSelfLog` writes `logs/serilog-selflog.txt` in **every** environment (the replacement for NLog's `internalLogFile`) -- check it first when the table stops filling.
  - **Routing rules**: the `ShouldPersist` filter on the database sub-logger -- request rows reach the database at `Information`, every other logger needs `Warning`+ to get in. `Channel` distinguishes `Request` rows from `Api` rows.
  - **Levels are spelled out**: `Information`/`Warning`/`Verbose`, not NLog's `Info`/`Warn`/`Trace`. `Logs.Level` is `nvarchar(16)` for this reason, and the `SerilogLogColumnAdjustments` migration rewrites historical rows so the table carries one vocabulary.
  - **Bodies are never blindly buffered.** `RequestLoggingOptions` (the `RequestLogging` section of `appsettings.json`) holds a content-type **allowlist**, a byte cap, a sensitive-property list and ignored paths. `BoundedResponseBufferStream` defers the capture decision to the first write, when `Content-Type` is known, so file downloads and uploads are recorded as `[body omitted: <type>, <n> bytes]` rather than copied into memory. `LogRedactor` masks passwords/tokens/etc. in JSON and form bodies, and is also applied by `PerformanceBehavior` before it logs a slow request.
  - `PerformanceBehavior` warns on handlers slower than 500 ms, logging the **redacted** request.
  - `LogRetentionService` (Infrastructure, `LogRetention` config section) purges rows past the retention window (default 90 days) in batches. Not registered when `UseInMemoryDatabase` is true.

## Known state / gotchas

- **Domain events are dispatched before the commit, and there is no outbox.** `ApplicationDbContext.SaveChangesAsync` publishes queued events and *then* persists, so a handler observes uncommitted state, and if the save subsequently fails the events have already been published — with no way to retract them. Nothing in the sample domain is harmed by this today (the handlers only log), but any handler that sends mail, calls another service or writes elsewhere would be building on it. Fixing it properly means dispatching after commit and adding a transactional outbox so the events and the rows land atomically; that needs its own design pass and is deliberately not bolted on here. Treat it as a known limitation, not as a pattern to copy.
- **Confirming a parked operation and executing it are two transactions.** `ConfirmOperationCommandHandler` commits the `Confirmed` transition *before* re-dispatching the captured command, so if execution then fails — a transient database error, or `ApplicationAlreadyProcessed` because somebody actioned the loan first — the operation is already spent and the initiator has to start over. This is the safe direction, and it is chosen rather than inherited: an operation never executes twice and never executes unconfirmed. It also cannot currently be improved on, because it depends on the limitation above — domain events dispatch before `SaveChanges` with no outbox, so a rollback would unpublish nothing. `ConfirmOperationCommandHandlerTests.Confirm_WhenTheCapturedCommandFails_LeaveTheOperationSpent` pins the behaviour so it is not "fixed" into a replay. **Do not reorder those steps.**
- **Controller-level authorization does not re-run on the confirm path.** `ISender.Send` re-enters the MediatR pipeline, not MVC, so the `[Authorize]` on `LoanApplicationController` is not evaluated when a captured command finally executes — only the one on `OperationsController` was. Today this changes nothing: all three protected controllers carry a **bare** `[Authorize]` with no roles or policies, so "authenticated" is the only requirement either way, and the confirmation policy is a *stricter* check than the endpoint's own. It becomes a real hole the moment someone adds `[Authorize(Roles = "Approver")]` to a controller holding a confirmable command, because the initiate call would be gated and the confirm call would not. The fix, if that day comes, is to carry the requirement on `[ConfirmableOperation(..., RequiredRole = "...")]` and check it in the confirm handler beside the actor policy, so authorization travels with the operation rather than with the route. It is deliberately **not** built now — an authorization mechanism nothing exercises is its own risk.
- `WebApi/Dockerfile` still targets .NET 7 base/SDK images while the projects target net10.0 -- update the tags before relying on `docker-compose`.
- Deliberate misspellings/inconsistencies are load-bearing for existing `using`s: the folder `WebApi/Middlwares`, and the namespaces `WebUI.Filters` / `WebUI.Services` inside the WebApi project. (`CreateApplicationCommandhandler` was **not** one of them — nothing referenced it by name outside its own test, since handlers are resolved by interface, so it is now spelled `CreateApplicationCommandHandler`.)
- `WebApi/Filters/SwaggerAttributes.cs` is excluded from compilation via `<Compile Remove>`.
- `WebApi/ClientApp` contains only build output and empty folders (no `package.json`, nothing tracked under `src`); the Angular app is not part of this template -- only the generated `WebApi/ApiClient/web-api-client.ts` is.
- **AutoMapper is 16.2.0, and that is a licensing decision as much as a version bump.** It was previously pinned to 14.0.0 (MIT) specifically to stay off the commercial gate, but 14.0.0 is vulnerable to [CVE-2026-32933](https://github.com/advisories/GHSA-rvv3-g6hj-g44x) (CVSS 7.5): AutoMapper enforced no recursion-depth limit, so a crafted deeply-nested object graph raises `StackOverflowException` and takes the whole process down — unrecoverable, and reachable from any endpoint that maps request input. The advisory is fixed only in **15.1.1+ / 16.1.1+**, all of which are commercially licensed (Lucky Penny), so the pin and the CVE were mutually exclusive. Consequences to know:
  - Startup logs `You do not have a valid license key for the Lucky Penny software AutoMapper ... required to have a licensed version` in production. **The same warning already appeared for MediatR 13.1.0**, so the gate was being tripped before this change — the pin was no longer buying what it was documented to buy.
  - A production deployment needs licences for both, *or* AutoMapper has to go. Dropping it is genuinely small now: the read side is three `ProjectTo` query handlers and three `IMapFrom` DTOs, all replaceable with hand-written `.Select(...)` projections, which would also delete this whole class of dependency risk.
  - API change worth remembering: 16.x removed `AddAutoMapper(params Assembly[])` (now `AddAutoMapper(cfg => cfg.AddMaps(assembly))`) and `MapperConfiguration` requires an `ILoggerFactory` (tests pass `NullLoggerFactory.Instance`).
- `dotnet build` emits duplicate/prunable `PackageReference` warnings (`NU1504`, `NU1510`) in `Infrastructure`/`WebApi`. No `NU1903` warnings remain — `dotnet list package --vulnerable` is clean.
